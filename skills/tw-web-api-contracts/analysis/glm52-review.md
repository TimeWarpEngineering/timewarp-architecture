### GLM 5.2 (OpenCode) — 2026-07-01

**Overall:** Consensus is mostly right but soft on three fronts: it over-values ceremony around serialization tests, it under-risks the published-package rename, and it universalizes a one-repo auth pattern. Two of the "unanimous" decisions I dissent from; two more I'd reframe.

**Decision 1 (casing):** AGREE (discover-first; kebab in TWA examples) — The strongest counter: "discover-first" is a cop-out that yields inconsistent skills across repos, because agents following the skill in repo A will paste kebab, in repo B will paste Pascal, and the skill's *examples* can only pick one. A skill that hedged on casing isn't a spec, it's a questionnaire. But the alternative — global PascalCase — is worse here for a concrete reason: the skill ships *inside* `timewarp-architecture`, where every contract path is `features/...` kebab (verified: 24/24 files under `source/container-apps/web/web-contracts/features/`). If examples say `Features/Admin/SecurityRole/`, every agent applying this skill in its own repo writes code that fails the existing tree. My call: keep the lean, but tighten it — **kebab is the TWA-canonical form and the skill's example form; Pascal is a one-line "if this repo is PascalCase (e.g. copic) mirror it"** — not a symmetric "either." Point 4 bug (case-sensitive `**/Features/**` globs) is real and must be fixed regardless.

**Decision 2 (plurality):** AGREE (plural) — Steelman for singular: the skill's "singular folder + plural namespace" story is the one genuinely elegant invariant in the document — it means the folder is an *entity slice* and the namespace is a *membership set*, two different things, and copic's `Admin/SecurityRole/` + `...SecurityRoles` namespace is the proof. Dropping the narrative loses that mental model. But TWA is 100% plural and well-formed (`features/admin/roles/`, `source/.../create-role.cs:1` → `Features.Admin.Roles`), the TWA docs say plural (`HowToWrite...:15`), and copic is internally inconsistent (Pascal `SecurityRole/` singular *and* `Announcements/` plural — verified dir listing) so it cannot be cited as authority. Plural + invariant-namespace wins. Note: this contradicts `SKILL.md:46` ("Singular, domain-oriented") and `examples.md:185-188` (the "intentional mismatch" table) — those passages become dead text under this vote and must be deleted, not just amended. The RFC undersells how much skill prose has to be unwritten.

**Decision 3 (tests):** DISSENT — The strongest case for "keep round-trips in `web-spa-integration-tests/Serialization/`": copic's `CreateSecurityRole_Tests.cs` does `parsed.Should().BeEquivalentTo(command)` round-trip on POCOs with default `System.Text.Json`. For a class whose properties are all `{ get; set; }` auto-properties and no custom converters, this assertion is *tautological* — json round-trips by construction. The real bug `*Contracts.Tests` has ever caught in copic is the camelCase `PropertyNamingPolicy` configuration, which is one global setting you can verify once in a single integration test (`tests/.../JsonSerializerOptions_Serialization_Tests.cs`, already present, already asserts `.ShouldBe`). Adding a `web-contracts-tests` project per contract for a passing-by-construction round-trip is CI surface + a `csproj` + a project reference + Fixie convention + one file per endpoint that can never fail *unless the contract author added a custom converter* — and converters aren't allowed by this skill anyway. Where the test has teeth — when a contract has `required` CTOR params, private setters, or `init`-only properties that deserialization must thread through — the contracts are mostly `set` on bindables (`create-role.cs:9-10`) and `required init` on trivial responses (copic `CreateSecurityRole.cs:34-35`), so even those tests are checking that `System.Text.Json` honors `init` accessors — which is .NET-SDK behavior, not a contract property. **My vote: keep round-trips in integration tests, BUT narrow the skill's requirement to "add a contract test when the contract uses `required`, `init`, custom converters, or non-default constructors; otherwise no dedicated test needed."** This is the only version that pays for itself, and it lets `web-contracts-tests` stay absent from TWA without calling that non-compliance.

**Decision 4 (assertions):** THIRD OPTION — Both prior reviewers buck-passed on FluentAssertions' licensing situation (the v8 commercial license change in 2025) while voting to add it as a "copic-dialect footnote." The repo-neutral stance here should be: **the skill should teach the assertion library as a parameterized placeholder, not anchor either.** "Shouldly" in TWA examples is fine, but `examples.md:178` (`parsed.Should().BeEquivalentTo(command)`) and `Tier 4` in particular hard-codes FluentAssertions' `BeEquivalentTo`, which is the one assertion whose semantics differ between Shouldly and FluentAssertions (referential vs structural equality) — exactly the place you don't want a hidden dialect divergence. My call: examples say "assert the parsed value equals the source using the repo's assertion library," one inline Shouldly example for TWA, one inline FluentAssertions example for copic. Refusing to pick is not weak; it's correct when the two predicates genuinely diverge. Composer's "imports a second assertion dialect for no gain" ignores that the dialects *are not interchangeable here* and that licensing gives copic a reason to migrate later.

**Decision 5 (Create Response):** AGREE (mixed) — Steelman against "mixed": a skill with two allowed shapes for the same construct ("required init for trivial; ctor+Guard for invariants") typically collapses in practice to whichever the agent remembers. Copic's split is defensible *only if you can articulate the trigger*, and the trigger "trivial id-only" is doing real work: copic `CreateSecurityRole.cs:34` returns both `SecurityRoleId` and `B2CGroupId` — two ids — and uses `required init`; the TWA `create-role.cs:24-30` Response echoes one `Guid RoleId` with a Guard; and the rationales track (copic's "newly created resource handles," TWA's "guard enforces server contract"). The mix is principled. **Caveat the prior reviewers missed:** the trigger should be "no domain invariants," not "trivial count of properties," because `required init` skips `Guard` and therefore *cannot* reject `Guid.Empty`. Copic's `CreateModule.cs` (`required Guid? B2CGroupId`) actually demonstrates the hole — `Guid.Empty` / `null` flows unchecked. The skill must say mixed, with the discriminator being *invariants*, not property count.

**Decision 6 (IAuthApiRequest):** DISSENT — Steelman for promote: the interface already lives in `source/foundation/foundation-contracts/base/i-auth-api-request.cs:1` (a *foundation package* — cross-repo by design), so "promote to canonical" is mostly documentation, not new code. Copic's absence is omission not rejection. **But:** (a) copic has shipped for years *without* this and the BFF there derives the user from the token server-side — that is not a bug, it is a competing design where the BFF never knows `UserId`. Promoting TWA's "BFF carries `UserId`, server re-validates it" to canonical silently declares the copic design wrong. (b) Sequencing: documbing `[IAuthApiRequestMixin]` as the canonical attribute name *now* locks an ugly Moxy-residue name into the skill, **three weeks before 053-002 renames it to `[AuthApiRequest]`** (Decision 8). So promoting now means the skill text churns twice. (c) TWA itself is internally split on the *form*: `get-roles.cs:13` uses `[IAuthApiRequestMixin]` (attribute) while `get-role.cs:13` declares `Guid UserId` *manually* with `IAuthApiRequest` — both patterns present in the same feature folder. The skill cannot declare "canonical" cleanly because the source can't even pick one mechanism. **My vote: document `IAuthApiRequest` as an *available* pattern, describe both the attribute and manual form with the preference (attribute when no other auth-side touches needed; manual when you would anyway), and hold the "canonical" label until after 053-002 produces the post-rename name.** This is a sequencing dependency with Decision 8 the prior reviewers flattened.

**Decision 7 (nullability):** AGREE (keep + fix) but soften — Steelman for relax: `string? + NotEmpty()` is *not* a silent-data bug at runtime — the validator rejects `null` before the handler runs, so functionally nothing breaks; the rule's value is purely that `string` + `null!` lets the compiler *help* and that `= string.Empty` + `NotEmpty()` is the real silent bug (JSON omits the field, `""` is left, `NotEmpty()` passes). Bundling the `string?` case with the `string.Empty` case overstates the danger of the former. Copic has 17 violations across production contracts that have run fine for years. **But:** the `= string.Empty` silent-bug case is real and TWA's `todo-items/create-todo-item.cs:11` and `:15` fall into exactly that case (`Title = string.Empty` + `NotEmpty()`), which is genuinely dangerous — JSON omission yields `""`, validator passes, silent wrong data. So the rule is right for the right reason; what the skill should say is *"forbidden: `string.Empty` on required; discouraged: `string?`+`NotEmpty()` (functional but compiler-disarmament)."* The two are not equal sins and treating them as equal has burned neither prior reviewer. Fix TWA's `hello`/`analytics`/`todo-items` — they're small and concrete — but the skill should distinguish the two patterns, not blob them.

**Decision 8 (053-002 sequencing):** DISSENT — The author + Composer worry about double-edit churn; churn is cheap, package release coordination isn't. **Hardest counter:** `[RouteMixin]` ships in the **published `TimeWarp.Foundation.Contracts` package** (`foundation-contracts-generators/contracts-mixin-generator.cs:23,270`), and the FastEndpoint generator matches it **by hardcoded string** `"TimeWarp.Architecture.RouteMixinAttribute"` (`models/endpoint-metadata.cs:31`). A rename is not a contract-files find/replace — it is: version-bump the package, republish (memory says this is already overdue, the `2.0.0-beta.2` tag is released and the next publish needs a bump), update the analyzer's by-name match, and **every generated app from this template until the consumers republish is on the old name unless their package ref pins to the new version**. Composer's "front-load the rename" treats this as local cleanup; it's a downstream-template-breaking release. Meanwhile the skill rewrite *doesn't need the final name in code at all* — `SKILL.md` is prose. The skill can describe the contract shape using `[Route]` (the target name) with a single migration note ("as of version X this attribute is `[RouteMixin]`; it will be renamed in 053-002"), and the TWA repo cleanup can proceed against the *current* `[RouteMixin]` name in parallel with whoever owns 053-002. The double-edit cost (one find/replace `[RouteMixin]`→`[Route]` when 053-002 lands) is ~30 seconds; the cost of blocking all contracts cleanup behind a package release is weeks. **My vote: third option — rewrite skill against the target name with a migration note, clean contracts against current `[RouteMixin]`, do 053-002 whenever it's ready; do NOT gate the cleanup on the rename.** This decision and Decision 6 are coupled (promoting `IAuthApiRequest` to "canonical" *also* locks the pre-rename attribute name), and the prior consensus resolved neither cleanly.

**Where the consensus is weakest:** Decisions 6 and 8 are not independent, and both reviewers treated them as such. The `[IAuthApiRequestMixin]` attribute name is one of the things 053-002 renames (`→ [AuthApiRequest]`), so "promote IAuthApiRequest now" + "rename first" are mutually entangled in a way both ballots hand-wave. Also, the reviewers accepted the "copic is mixed, therefore plural" syllogism without noting it's a weak sample: copic mixed means copic can't *vouch* for plural, it doesn't mean plural is better — TWA-consistency is the actual winning argument and they under-argued it.

**Anything all three reviewers missed:**
1. **The generator emits `GetAuthQueryParameters()` as `private`** (`contracts-mixin-generator.cs:193`), but `get-roles.cs:20` calls it from the same partial class — fine — yet `get-role.cs:13` declares `UserId` *manually* and `[IAuthApiRequestMixin]` is absent there. So TWA's two admin queries demonstrate that the attribute form and manual form are **not equivalent**: the attribute form also synthesizes `GetAuthQueryParameters()` for query-string composition. The skill needs to spell out that manual `IAuthApiRequest` is for POST/GET-by-id (no query-string auth), attribute form is for list queries with `IQueryStringRouteProvider`. Neither prior reviewer noticed this mechanism difference.
2. **`Required` + `init` Create responses have a real `Guid.Empty` hole** (cop `CreateModule.cs` `required Guid?`). Decision 5's mixed shape only holds if the discriminator is *invariants*, not *triviality*. Reviewers fixed the wrong axis.
3. **FluentAssertions licensing** (commercial license change since v8, 2025) — neither reviewer weighed this when voting Shouldly vs FluentAssertions. It materially affects whether the skill should *promote* FluentAssertions in any example, even as a "copic dialect footnote."

If it's a delegate alias both repos use, fine; if copic's 45 `IMockResponseFactory` *implementor classes* are isomorphic to this delegate (which Composer's matrix suggests they aren't), the "detection" section needs to say so. This is the one place the skill may be teaching a shape that doesn't exist in the other repo at the *type* level.
