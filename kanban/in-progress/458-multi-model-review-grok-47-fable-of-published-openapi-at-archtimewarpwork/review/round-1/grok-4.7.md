### G-001 — Cookie-session operations are published with no security requirement

- **Severity:** major
- **Lens:** security
- **Pointer:** `/paths/~1api~1Roles/get`, `/paths/~1api~1Roles/get/responses/401`, `/paths/~1api~1settings/get`, `/paths/~1api~1admin~1feedback~1{feedbackItemId}~1replies/post`, `/paths/~1api~1admin~1feedback/get/security`, `/paths/~1api~1Feedback~1attachments~1{attachmentId}/get/security`, `/components/securitySchemes/JWTBearerAuth`
- **Evidence:** There is no root `security`. 58 operations omit `security`. 34 of those document `401` and are session-authorized in source (`[EndpointAuthorize]` with `IdentitySession`), including `GET /api/Roles`, `GET /api/settings`, `PUT /api/settings`, the xAI key routes, and `POST /api/admin/feedback/{feedbackItemId}/replies`. Live unauthenticated `GET` of `/api/Roles`, `/api/Roles?userId=00000000-0000-0000-0000-000000000001&returnTotalCount=false`, `/api/admin/principals?...`, `/api/Feedback`, `/api/settings`, `/api/settings/entra-tenant?domain=contoso.com`, `/api/Users/Current/xai-api-key`, `/api/admin/ai/xai-api-key`, and `/api/agent-chat/configuration` each returned **401 with an empty body and no `WWW-Authenticate`**. The host fails closed. The document still tells an OpenAPI client those calls are unsecured. The only scheme is `JWTBearerAuth`. `OpenApiBearerSecurity` attaches it only when the endpoint lists the agent-token scheme (`source/foundation/foundation-server/open-api-bearer-security-server.cs` lines 18–19 and 128–132), so cookie-only routes are left blank. Sibling proof: `GET /api/admin/feedback` requires `feedback:read`, while admin reply on the same resource has no `security` because its contract lists only the session schemes (`reply-to-feedback-contracts.cs`). `GET /api/Feedback/attachments/{attachmentId}` publishes bearer with an empty scope array and omits the human session its `Configure` also accepts. `GET /api/identity/entra/challenge` is the exception: it is anonymous and its 401 is a ceremony outcome, so it should stay unsecured.
- **Proposed fix:** Add a session-cookie security scheme and set `security` from `[EndpointAuthorize]` / `AuthenticationSchemes`. Where session and agent token are both accepted, publish two requirement objects (OR). Publish `security: []` on intentionally anonymous operations so they are distinct from a missing requirement. Add a document test: every operation with a 401 response has a security requirement, with an allowlist of one for the Entra challenge.
- **Owner:** transformer — `source/foundation/foundation-server/open-api-bearer-security-server.cs` (cookie scheme beside it). Contract auth attributes are already the source.

### G-002 — PrincipalId and CredentialId schemas have no JSON type

- **Severity:** major
- **Lens:** contracts
- **Pointer:** `/components/schemas/TimeWarpIdentityPrincipalId`, `/components/schemas/TimeWarpIdentityCredentialId`, `/components/schemas/SystemNullableOfTimeWarpIdentityPrincipalId`, `/components/schemas/TimeWarpArchitectureFeaturesIdentityGetCurrentSession_Response/properties/principalId`
- **Evidence:** `TimeWarpIdentityPrincipalId` is only `{"description":"Stable typed identity for a principal — server-minted and distinct from CredentialId."}`. `TimeWarpIdentityCredentialId` is description-only. `SystemNullableOfTimeWarpIdentityPrincipalId` is `{}`. Session `principalId` is `oneOf` [`{"type":"null"}`, a `$ref` to that empty schema], and the property is required. Those typed ids are referenced from registration, token, and admin principal responses (10 refs for `PrincipalId`, 4 for `CredentialId`). Source says the `[TypedId]` converter writes a plain Guid string (`source/libraries/timewarp-identity/principals/principal-id.cs` lines 7–8). Live `GET /api/identity/session` returned `{"isAuthenticated":false,"principalId":null,...}`, which matches the null arm only. A generated client has no `type`/`format` for the authenticated value, so Kiota/NSwag emit an unconstrained model. Guid lists in the same document are `string` + `format: uuid`, so the exporter can express a Guid when the property is `System.Guid`.
- **Proposed fix:** Teach the schema exporter, or a schema transformer, that a `[TypedId]` (and `Nullable<T>` of one) is `type: string`, `format: uuid`. Add a build check that fails when a component schema is `{}` or has a description and no `type`.
- **Owner:** generator — `source/analyzers/timewarp-architecture-analyzers/generators/typed-id-emitter.cs`, plus the OpenAPI schema pipeline in `source/foundation/foundation-server/`.

### G-003 — Feedback attachment upload and download are documented as JSON objects

- **Severity:** major
- **Lens:** contracts
- **Pointer:** `/paths/~1api~1Feedback~1attachments/post/requestBody/content/image~1png/schema`, `/components/schemas/TimeWarpArchitectureFeaturesFeedbackUploadFeedbackAttachment_Command`, `/paths/~1api~1Feedback~1attachments~1{attachmentId}/get/responses/200/content/application~1json`, `/components/schemas/TimeWarpArchitectureFeaturesFeedbackDownloadFeedbackAttachment_Response`, `/components/schemas/SystemIOStream`
- **Evidence:** Upload advertises `image/png`, `image/jpeg`, `image/gif`, `image/webp`, `application/pdf`, and `text/plain`, and each schema is the command object `{content, fileName, contentType}` whose `content` is `SystemIOStream` (`type: string`, `format: binary`). The binder reads the raw body and takes the file name from `X-File-Name` (`source/container-apps/web/features/feedback/upload-feedback-attachment/upload-feedback-attachment-binder-server.cs` lines 25–38; header constant `source/foundation/foundation-contracts/services/file-upload-headers.cs` line 16). That header is not a parameter. Download's 200 is `application/json` with required `content`, `contentType`, and `fileName`. The endpoint writes the bytes with the file's content type, `Content-Disposition`, `X-Content-Type-Options: nosniff`, and `Cache-Control: private, no-store` (`download-feedback-attachment-endpoint-server.cs` lines 51–64). A generated client will POST a JSON object and JSON-parse an image.
- **Proposed fix:** For `IFileUploadRequest`, publish a binary body (or the raw stream) plus a required `X-File-Name` header, and stop emitting `fileName`/`contentType` as JSON fields. For the download endpoint, publish the success body as the file bytes (`content` schema `string`/`binary`) with the allow-listed media types, and document `Content-Disposition`. Add a document test that a response whose CLR type contains `Stream` is not `application/json`.
- **Owner:** transformer, driven by the hand-written endpoints `upload-feedback-attachment-endpoint-server.cs` and `download-feedback-attachment-endpoint-server.cs`. The contracts comment already says the generated JSON endpoint cannot serve this route.

### G-004 — A validation failure is application/json and carries `errors`, which the problem schema omits

- **Severity:** major
- **Lens:** doc-vs-reality
- **Pointer:** `/paths/~1api~1Hello/get/responses/default/content/application~1problem+json`, `/components/schemas/TimeWarpFoundationTypesSharedProblemDetails`, `/paths/~1api~1admin~1feedback/get/responses/401/content/application~1problem+json/schema`
- **Evidence:** `GET /api/Hello` with no `name` returned **400** `content-type: application/json; charset=utf-8` and `{"type":"https://tools.ietf.org/html/rfc7231#section-6.5.1","title":"One or more validation errors occurred","status":400,"detail":"'Query:Name' must not be empty.","errors":{"name":["'Query:Name' must not be empty."]}}`. The operation's only error is `default` with `application/problem+json` and `TimeWarpFoundationTypesSharedProblemDetails`, whose properties are `type`, `title`, `status`, `detail`, `instance`. There is no `errors` property and no `additionalProperties` entry. The same component is the `default` body on 73 operations. `MicrosoftAspNetCoreMvcProblemDetails` is a second copy of that shape, used by the Entra challenge. Bearer `401`/`403` use a third inline object limited to non-null `title`, `status`, and `detail` (`open-api-bearer-security-server.cs` lines 226–237). The serialization test requires the `errors` dictionary and `traceId` to survive as extension data (`tests/container-apps/web/web-contracts-tests/types/shared-problem-details-serialization-tests.cs`).
- **Proposed fix:** Make FluentValidation failures `application/problem+json` and add an explicit `400` that uses one problem schema. On that schema, declare `errors` (`additionalProperties` of `string[]`) and allow the extension bag (`traceId`). Point bearer `401`/`402`/`403`/`503` at the same component instead of a fresh inline object. Add a probe test that `GET /api/Hello` without `name` is `application/problem+json` and that the published schema lists `errors`.
- **Owner:** host config for the validation writer (FastEndpoints setup in `source/foundation/foundation-server/common-server-module.cs`) and transformer `open-api-one-of.cs` / `open-api-bearer-security-server.cs` for the schema.

### G-005 — Request bodies omit `required` for fields the validators reject when empty

- **Severity:** major
- **Lens:** contracts
- **Pointer:** `/components/schemas/TimeWarpArchitectureFeaturesAdminRolesCreateRole_Command`, `/components/schemas/TimeWarpArchitectureFeaturesAgentLinksRequestAgentHumanLink_Command/required`, `/components/schemas/TimeWarpArchitectureFeaturesAgentChatsSetUserXaiApiKey_Command`
- **Evidence:** 33 of 34 `*_Command` schemas have properties and no `required` array. `CreateRole` publishes optional `userId`, `name`, and `description`. The xAI key command publishes optional `apiKey` while its description says the key is required. The one exception is `RequestAgentHumanLink`, whose `humanPrincipalId` is required because the property has `[Required]`. That contract says the attribute exists only to mark OpenAPI, and the validator is the runtime rule (`request-agent-human-link-contracts.cs` lines 9–11). FluentValidation `NotEmpty` does not reach the document, so NSwag/Kiota treat names, signatures, challenges, and API keys as optional and omit them.
- **Proposed fix:** Emit `required` from non-nullable properties and from `NotEmpty` / `NotNull` rules (the same rules the handler already runs). Keep `[Required]` as a backfill only where the validator cannot see the member. Add a document check that a command property with a `NotEmpty` rule is in `required`.
- **Owner:** generator / schema pipeline. The skill should say the validator is the source of `required`, in `skills/tw-web-api-contracts/`.

## What looks right

- The snapshot matches the live document byte for byte (SHA-256 above). `openapi` is `3.2.0`. OperationIds are unique (79).
- `OneOf<Response, SharedProblemDetails>` is not published as the OneOf struct. Success is `200` `application/json` and the problem arm is `default` `application/problem+json` (73 operations), which is what `open-api-one-of.cs` describes. The remaining gap is G-004 (validation's real content type, and the `errors` bag).
- Nullable strings and integers use `type: ["null", "string"]` / `["null", "integer"]`, which is valid JSON Schema 2020-12. Enums are strings named by the CLR member (`Passkey`, `Microsoft365`, feedback status, and the rest). Live `GET /api/identity/sign-in-methods` returned `{"methods":["Passkey"]}`.
- Anonymous reads that the document leaves open behaved as described: `GET /api/Hello?name=review` → 200 `{"message":"Hello, review!"}`; `GET /api/Users/Current/Profile` → 200 with `email: null` and a data-URI `avatar`; `GET /api/settings/assistant` → 200 `{"name":"Akili",...}`; `GET /api/identity/session` → 200 `isAuthenticated: false`, `principalId: null`, empty `roleIds` and `permissions`.
- Cookie-session 401s that have no response `content` matched the host: empty body, no `WWW-Authenticate`. The defect is the missing `security` requirement (G-001), not a hidden problem body.
- Agent routes that list the agent scheme do publish `JWTBearerAuth` and a scope: `feedback:read`, `feedback:note`, `feedback:severity`, `feedback:status`, `identity:read`, `demo:invoke`, `credential:manage`.
