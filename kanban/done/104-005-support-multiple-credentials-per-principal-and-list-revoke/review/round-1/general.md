- Suggestion: No action required in this task; add/append to the existing kanban note tracking the 110 finding so the accumulating cost is visible when the analyzer is scheduled. Not blocking.

### Issue 2 — Severity: nit
- File: tests/container-apps/web/web-server-integration-tests/Features/Identity/Credential_List_Tests.cs:159-160 (and the contract-test twin at tests/container-apps/web/web-contracts-tests/features/identity/identity-contracts-serialization-tests.cs:377-378)
- Description: The load-bearing no-secret-material pin uses `json.ToLowerInvariant().ShouldNotContain("handle")` / `"publicmaterial")`. Because `CredentialSummary` carries a caller-supplied `string? Label`, the substring check is content-fragile in the false-POSITIVE direction: a credential labelled e.g. "phone passkey handle" would fail the wire assertion even though nothing leaked (today's fixtures use null/"laptop"/"phone" labels so it never trips). It is also imperfect in the false-NEGATIVE direction (a future leaked field named `RawKey` would serialize as `"rawKey"` and slip past both substrings) — though the structural omission (the type simply has no such property) is the real guarantee, correctly documented as the primary layer with the wire-check as the survives-serialization backstop.
- Suggestion: Consider asserting the exact absence of the JSON property keys (parse and check `!root.EnumerateObject().Any(p => p.Name is "handle" or "publicMaterial")` on each summary) rather than a whole-body substring, which is both label-robust and precise. Low priority — the structural guarantee carries the real weight.
- Status: open

### Issue 3 — Severity: nit
- File: source/container-apps/web/web-application/features/identity/add-passkey-handler.cs:66 (challenge consume) and add-agent-key-handler.cs (same shape); overlaps the security review
- Description: Brief overlap note, not a duplication of the security lens: AddPasskey consumes a `WebAuthnCeremonyType.Registration` challenge and AddAgentKey an `AgentKeyCeremonyType.Registration` challenge — the SAME ceremony type the anonymous new-principal `CompletePasskeyRegistration`/`CompleteAgentKeyRegistration` handlers consume, since both add-handlers deliberately reuse the anonymous `Start*` endpoints (per Decision 4). So there is no domain separation between "register a brand-new principal" and "attach to the current principal" at the challenge layer — the two flows are distinguished only by endpoint auth and by which principal id the handler supplies to `Credential.Create`. The functional outcome is sound (a valid fresh attestation is required either way, and the authenticated add-endpoint sources the principal from the accessor), and the `excludeCredentials`-absent gap is already recorded as a follow-up; flagging only that the shared ceremony-type itself is not called out in either add-handler's Design region. Whether the shared type enables any confused-deputy is the security reviewer's call.
- Suggestion: One sentence in the add-handlers' Design regions noting the deliberate reuse of the anonymous Registration ceremony type (so a future reader doesn't assume a dedicated authenticated ceremony type exists), and defer the security judgement to that review.
- Status: open
