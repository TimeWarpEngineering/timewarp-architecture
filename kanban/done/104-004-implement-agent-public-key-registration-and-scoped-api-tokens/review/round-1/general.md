## Issues

### Issue 1 — Severity: bug
- File: source/container-apps/web/web-contracts/features/identity/commands/complete-agent-token-issuance.cs:50-51
- Description: `RuleFor(x => x.Scopes).NotEmpty().Must(scopes => scopes.Count <= 16)` throws `NullReferenceException` when `Scopes` is null. FluentValidation's default rule-level cascade is Continue (no global `CascadeMode` is configured anywhere in the repo — verified), so after `NotEmpty` fails on null the `Must` predicate still executes and dereferences null. Empirically confirmed against FluentValidation 12.1.1 with this exact rule chain: `Validate(new Cmd { Scopes = null! })` → `THREW: NullReferenceException`. STJ happily assigns null for a JSON `"scopes": null`, so `POST /api/identity/agent/token` with `{"keyId":"x","challenge":"x","signature":"x","scopes":null}` — an anonymous endpoint — produces an unhandled exception in `FluentValidationBehavior` (500) instead of the 400 validation problem, violating the task's own "machine-readable errors" requirement. The string-field rules are unaffected (`MaximumLength` treats null as valid by design); only the collection `Must` is null-unsafe. `RuleForEach` handles the null collection gracefully, so it does not mask the issue.
- Suggestion: Make the predicate null-safe (`scopes => scopes is null || scopes.Count <= 16`) or set `.Cascade(CascadeMode.Stop)` on the Scopes rule. Add two cheap validator/round-trip tests: `scopes: null` → validation error (not an exception), and `scopes: []` → validation error.
- Status: open

### Issue 2 — Severity: bug
- File: source/libraries/timewarp-identity/tokens/i-agent-token-store.cs:12-15 (echoed at source/container-apps/web/web-server/services/agent-token-authentication-handler.cs:21-23)
- Description: The port's Design region states "Opaque tokens are LIVE-REVOCABLE: **Validate re-reads the principal on every call**, so a quarantine takes effect immediately for every already-issued token." `IAgentTokenStore.Validate(string)` does no such thing — it has no access to `IPrincipalStore` and returns a grant purely from the token dictionary (in-memory-agent-token-store.cs:63-82). The principal liveness re-read that actually delivers the quarantine cutoff lives exclusively in `AgentTokenAuthenticationHandler.HandleAuthenticateAsync` (agent-token-authentication-handler.cs:97-102), i.e. it is a WEB-SERVER caller obligation, not a port/store property. The auth handler's own Design region repeats the misattribution ("IAgentTokenStore's opaque, store-backed design re-reads the principal on every Validate call — see that port's Design region"). This is the repo's Design-region-describes-behavior-the-code-doesn't-have bug class, and it is load-bearing rather than cosmetic: the same paragraph names 104-013's x402 settle-time check as depending on this exact live-check property — a future consumer (settle-time validation, api-server bearer validation) that calls `IAgentTokenStore.Validate` directly and trusts the port doc gets NO quarantine cutoff, silently reopening the hole the opaque-token decision was made to close. Today's only caller happens to do the re-read, so no current behavior is wrong — which is precisely why only the doc will catch the next caller.
- Suggestion: Reword both regions to state the real contract: opaque tokens are live-revocable *because the validating caller must pair `Validate` with a principal liveness check* (the store deliberately knows nothing of principals); make the port's XML doc on `Validate` say "returns the grant — callers enforcing quarantine/liveness MUST re-read the principal (see AgentTokenAuthenticationHandler)". Alternatively (stronger, later): add a port operation that takes the liveness check into the seam so 104-013 cannot skip it.
- Status: open

### Issue 3 — Severity: nit
- File: source/container-apps/web/web-application/features/identity/complete-agent-token-issuance-handler.cs:100-103
- Description: Duplicate scope entries are accepted and propagated verbatim: `{"scopes":["identity:read","identity:read"]}` passes the validator (each entry known, count ≤16), is stored on the grant, emitted as two identical `timewarp:scope` claims by the auth handler, and echoed twice in the Response and in GetAgentIdentity's Scopes. Nothing breaks (`RequireClaim`/`HasClaim` are unaffected), but the token's advertised scope list is not canonical, which is mildly untidy for anything downstream that counts or diffs scopes (104-013 credit gating is scope-adjacent).
- Suggestion: Normalize once in the handler before `Issue` (`command.Scopes.Distinct(StringComparer.Ordinal).ToList()`), or note in the contract's Design region that duplicates are permitted and preserved.
- Status: open
