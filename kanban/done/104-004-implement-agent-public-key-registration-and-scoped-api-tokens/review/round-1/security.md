# Round 1 — security

**Date:** 2026-07-20
**Scope reviewed:** commit 16beaa46 vs parent (security lens) — `ceremonies/agent-key/**`, `tokens/**`, the agent registration/issuance/session handlers, and the web-server bearer scheme + scope policy

## Summary

The agent-key ceremony and token machinery are soundly built and carry the 104-003 round-1/round-2 lessons forward from day one. I verified each claim against the code: the SPKI parse guards empty/oversize BEFORE `ImportSubjectPublicKeyInfo`, rejects trailing DER via `bytesRead != Length`, pins the curve by comparing the imported key's P-256 OID (not spoofable — an explicit-parameters or P-384 key reads back a non-matching/`null` OID and is rejected), and catches `CryptographicException` (the M9 empty-input hole is closed here — empty is guarded before the call, and the guard is kept as defense-in-depth). The proof is domain-separated (`Register.v1:` / `Token.v1:`), DER-only (P1363 rejected), single fixed algorithm with nothing reading an alg from attacker data, and the challenge fed to `Verify` is store-gated by `TryConsume` — cross-ceremony replay fails **both** directions (tested). Tokens are 32-byte CSPRNG, SHA-256-hashed at rest (never logged — grep clean), expiry-enforced on `Validate`, and the hash-at-rest design neutralizes the dictionary-lookup timing concern (an attacker cannot steer `SHA-256(guess)` toward a stored key). The bearer scheme is structurally isolated: `IdentityReadPolicy` restricts `AuthenticationSchemes` to `agent-token` only, so a cookie-only request is never offered to this handler and 401s (tested with a real passkey cookie). Quarantine is post-verify (403) at issuance and a deliberate silent `Fail()`→401 at validation, both documented. Consume-before-verify, no-enumeration generic 400s, and the M3 duplicate-key `try/catch(InvalidOperationException)`→409 are all present. Negative-path unit and integration tests are honest — each would fail if its check were removed. One concrete defect (an attacker-triggerable 500 from a `null` scopes array), plus two minor items. No auth-bypass, no verification gap.

## Issues

### Issue 1 — Severity: suggestion
- File: source/container-apps/web/web-contracts/features/identity/commands/complete-agent-token-issuance.cs:51 (reached via source/foundation/foundation-contracts/behaviors/fluent-validation-behavior.cs:40; handler re-derefs at complete-agent-token-issuance-handler.cs:79)
- Description: `RuleFor(x => x.Scopes).NotEmpty().Must(scopes => scopes.Count <= 16)` throws `NullReferenceException` when `Scopes` is explicitly `null`. The property has an `= []` initializer, but System.Text.Json overwrites it with `null` for a request body containing `"scopes": null` (STJ does not enforce non-nullability of `List<string>`). FluentValidation's default rule-level cascade is `Continue` (confirmed — no `ValidatorOptions.Global`/`CascadeMode` override anywhere in `source/`), so the `Must` predicate still runs after `NotEmpty` records its failure and dereferences `null.Count`. `FluentValidationBehavior.Handle` calls `ValidateAsync` with no try/catch (fluent-validation-behavior.cs:38-41), so the exception propagates to an unhandled **500**. Reachable by any anonymous caller POSTing `{"keyId":"x","challenge":"x","signature":"x","scopes":null}` to `api/identity/agent/token`. Impact is bounded — the throw happens in the validation pipeline *before* the handler, so no challenge is consumed and no state changes; it is one 500 per request with no amplification, and in Development the exception page leaks a stack trace. Not an auth bypass. But it is an attacker-triggerable unhandled exception on trivially-malformed input, the same defect class as 104-003's M9, and the handler's own `command.Scopes.Where(...)` at line 79 would NRE identically if a null ever reached it.
- Suggestion: Guard the predicate — `.Must(scopes => scopes is not null && scopes.Count <= 16)` — or add an explicit `RuleFor(x => x.Scopes).NotNull()` (which then yields a clean 400 and keeps null out of the handler's `.Where`), or set that rule's `CascadeMode.Stop`. A one-line vector test (`"scopes":null` → 400, not a throw) pins it.
- Status: open

### Issue 2 — Severity: suggestion
- File: source/libraries/timewarp-identity/tokens/in-memory-agent-token-store.cs:52-55, 97-115 (Design region :17-20)
- Description: `EvictOldest` runs at `MaxEntries` (100k) and removes the entry with the earliest `ExpiresAt` — which is the oldest *still-valid* token, not necessarily an expired/abandoned one (expired ones were already swept by `PruneExpired`). Under a token-store flood (an attacker registers agents and issues tokens — unlimited by design, no sponsor/rate-limit until 104-015), a legitimate agent's unexpired token can be silently evicted, so its next request 401s before its stated `ExpiresInSeconds` elapses. This is within the documented accepted DoS posture (mirrors the challenge-store cap; rate-limiting is explicitly 104-015), and mounting it requires a full valid register+issue crypto ceremony per entry, so it is not cheaper than the baseline "unlimited principals" the plan already accepts. The Design region says the cap "mirrors InMemoryChallengeStoreCore" but does not state the security-relevant consequence that a *valid* bearer token can be dropped before expiry.
- Suggestion: Add one line to the Design region making explicit that at-cap eviction can invalidate a still-valid token early (an availability, not confidentiality, effect), and cross-reference 104-015. No code change required for Wave 1.
- Status: open

### Issue 3 — Severity: nit
- File: tests/container-apps/web/web-server-integration-tests/Features/Identity/Agent_Token_Tests.cs:49-61 (vs :64-90)
- Description: The no-enumeration-oracle guarantee (unknown KeyId, revoked credential, missing principal, and bad signature all return a byte-identical generic 400) is the central issuance security property, and the code upholds it (every path returns `IssuanceFailed()`). The bad-signature test asserts both `Status == 400` and `Title == "Token issuance failed"`, but the unknown-KeyId test asserts only `Status == 400`. So the tests only half-pin the equivalence — a future change that gave unknown-KeyId a distinct title/detail would not be caught by the unknown-KeyId test.
- Suggestion: Assert `Title == "Token issuance failed"` (and ideally `Detail`) in `BadRequest_Given_Unknown_KeyId` too, so both branches pin the identical shape.
- Status: open

## Coverage notes (not issues)

- Crypto negative paths are genuinely exercised and would each fail if the check were deleted: tampered signature / wrong challenge → `SignatureInvalid`; cross-ceremony replay **both** directions → `SignatureInvalid` (would pass without domain separation); wrong key → `SignatureInvalid`; RSA → `MalformedPublicKey`; P-384 → `UnsupportedAlgorithm`; P1363 → `SignatureInvalid` (would pass if dual-format were accepted); empty pubkey/sig/challenge → no throw; SPKI empty/oversize/truncated/trailing/garbage all rejected without throwing; keyId = SHA-256. Integration: scheme isolation via a real passkey-issued cookie → 401; no-header → 401 bare `Bearer`; garbage → 401 `invalid_token`; demo:invoke-only → 403 `insufficient_scope`.
- **Untested (latent, acceptable):** quarantine cutoff at validation (silent `Fail()`→401) and at issuance (post-verify 403) have no covering test because no code path sets a principal inactive until 104-005 — same gap as 104-003's passkey quarantine, and the ordering is correct for when quarantine ships. No scope-inflation path exists: issued scopes are the caller's request filtered to `AgentScopes.IsKnown`, and by design any Keyed agent may self-grant either known scope (`identity:read` reads only the caller's own principal; `demo:invoke` usage is credit-gated in 104-013) — documented, no privilege escalation.
