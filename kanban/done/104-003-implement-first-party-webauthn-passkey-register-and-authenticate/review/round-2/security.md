# Round 2 — security

**Date:** 2026-07-19
**Scope reviewed:** commit d2c16a74 (round-1 fixes M1–M8) vs 56882153, plus a defect scan of the 15-file fix delta

## Summary

All five security-relevant round-1 findings (M1–M5) are genuinely fixed in the post-fix code, and the two honesty/robustness items I re-checked (M6–M8 spot confirm) hold. The quarantine oracle (M2) is closed — `!IsActive` now runs strictly after `WebAuthnAuthentication.Verify` succeeds, and no other pre-verify branch leaks account state (the revoked/unknown paths both collapse to an identical generic 400). The duplicate-registration race (M3) is caught with the correct exception type at the correct (tight) scope. **However, the M5 fix introduced one new defect (M9): the exact-bit-length helper it added dereferences the first byte of the modulus without a length guard, so an attacker-supplied RSA COSE key with a zero-length modulus byte string throws an uncaught `IndexOutOfRangeException`** — breaking the library's explicitly documented "verification stays exception-free on the adversarial path" invariant and surfacing as an unhandled 500. One new bug; M5's intended behavior (2048-bit floor) is otherwise correct.

## Prior findings — re-verification

- **M1 (config binding) — confirmed fixed.** `appsettings.json` section renamed `WebAuthn` → `WebAuthnOptions`; the binding test (`WebAuthnOptions_Binding_Tests.cs`) sets `RpName` to `"Integration Test RP"` (distinct from the C# default `"TimeWarp Architecture"`), resolves `IOptions<WebAuthnOptions>` from the live host, and asserts the bound value — this **asserts a non-default value**, so it genuinely fails on the old section name (partial-bind masking cannot recur). RpId left unset and asserted still-`localhost`.
- **M2 (quarantine pre-auth oracle) — confirmed fixed.** `complete-passkey-authentication-handler.cs:93-97`: `!principal.IsActive → Quarantined()` now runs after `Verify` (line 87-91). The revoked-credential branch (`credential.IsRevoked`, :68) is *before* Verify but returns the **same** generic 400 as unknown/bad-signature, so it discloses no account state (it was already generic in round 1; ordering is defensible and documented — a revoked credential can never verify, so early-out is behavior-equivalent). Quarantine's distinct-403 premise is now actually true. No residual pre-verify state-leak branch.
- **M3 (dup-registration race) — confirmed fixed; orphan posture sound (see verdict below).** `complete-passkey-registration-handler.cs:102-112` wraps only the `AddCredentialAsync` await in `try/catch (InvalidOperationException) → CredentialAlreadyRegistered()` 409. Right exception type (the store throws `InvalidOperationException` from the `HandleIndex.TryAdd` collision branch) and tight scope (the following `IssueAsync` is outside the try, so unrelated IOEs are not swallowed). The catch also covers the store's other two IOE sites — "Principal does not exist" (unreachable here: the principal was just added under the same store) and a `CredentialId` GUID collision (effectively impossible) — both benign. Design region rewritten to state the real ordering and drop the blanket "never leaves an orphan" claim.
- **M4 (size caps) — confirmed fixed.** Both completion commands now cap every base64url field: registration CredentialId 2KB / ClientDataJson,AttestationObject 64KB; authentication CredentialId,UserHandle 2KB / ClientDataJson,AuthenticatorData,Signature 64KB. No new defect (MaximumLength on the optional UserHandle correctly tolerates null).
- **M5 (weak RSA modulus) — fixed for the stated concern, but introduced M9.** The 2048-bit floor is correct: `GetModulusBitLength` ignores leading zero bytes and counts bits in the top non-zero byte, so the 2048 boundary is **inclusive** (a proper 2048-bit modulus reads back exactly 2048 and passes; 2047 is rejected), and a leading `0x00` padding byte is handled. The vector test is **honest** — a 512-bit public-only fixture asserts `UnsupportedAlgorithm`; with the check removed, `RSA.ImportParameters` would import it and registration would return Success, failing the test. The defect is the missing empty-input guard (M9).
- **M6 (test fixture Design honesty + cookie isolation) — confirmed** (general-scope): per-class fixture sharing now documented; per-call fresh-cookie `HttpClient` helper isolates session assertions from run order.
- **M7 (session Response invariant) — confirmed fixed.** Ctor throws `ArgumentException` on `isAuthenticated != (principalId is not null)`. No new untrusted-input exception surface: this Response is server-produced only (the handler always passes an agreeing pair), never deserialized from attacker input server-side.
- **M8 (stale comment) — confirmed** reworded.

## Issues

### M9 — Severity: bug — Status: open (new; introduced by the M5 fix)
- File: source/libraries/timewarp-identity/ceremonies/webauthn/internal/cose-key.cs:181 (helper), reached from :154 (call site), catch at :165
- Description: `GetModulusBitLength` skips leading zero bytes with `while (index < modulus.Length - 1 …)` and then reads `byte leading = modulus[index];` (line 181). For a **zero-length** modulus the guard leaves `index = 0` and `modulus[0]` throws `IndexOutOfRangeException`. A zero-length modulus is reachable from adversarial input: `CoseKey.TryParse`'s RSA branch accepts an empty modulus (`crvOrNBytes = reader.ReadByteString()` returns a non-null `byte[0]` for a zero-length CBOR byte string, and the only guard at :117 is `is null`, which empty passes). `GetModulusBitLength` is called at :154 inside `TryCreateVerifier`'s try block, but that block's only catch (:165) is `catch (CryptographicException)` — `IndexOutOfRangeException` is **not** caught, so it propagates out of `TryCreateVerifier`, out of `WebAuthnRegistration.Verify` (whose surrounding `try/finally` only disposes, does not catch), and out of the handler (no catch) into the ASP.NET pipeline as an **unhandled 500**. This violates the invariant this very file and `webauthn-registration.cs`'s Design region assert: "every failure in this file is a Try* bool, never a throw, so … Verify stay[s] exception-free on the adversarial path." An anonymous caller who starts a real registration ceremony can craft an RS256 COSE key with `n` = empty byte string and force the 500. Impact is bounded (one 500 per request, each requiring its own issued+consumed challenge — no process crash, no amplification), and in Development the developer-exception page discloses a stack trace; it is not an auth bypass. But it is an uncaught exception on the adversarial path, which is exactly the fail-closed contract this module is built around.
- Suggestion: Guard empty input before dereferencing — e.g. `if (modulus.Length == 0) return false;` at the top of `GetModulusBitLength` (a zero-length modulus is trivially < 2048 bits), or reject empty `Modulus`/`Exponent` in `TryCreateVerifier`'s RS256 branch alongside the null checks, or broaden the catch to include the input-validation exception. A one-line vector test (empty-modulus RSA COSE key → `UnsupportedAlgorithm`, not a throw) would pin it, mirroring the M5 weak-key test.
- Status: open
