## Issues

### Issue 1 — Severity: bug
- File: source/container-apps/web/web-server/appsettings.json:29 (vs source/container-apps/web/web-application/configuration/web-authn-options.cs:24 and program.cs:281)
- Description: The appsettings section is named `"WebAuthn"`, but `AddFluentValidatedOptions<WebAuthnOptions, ...>` binds `configuration.GetSection(key)` where `key = [ConfigurationKey] ?? typeof(TOptions).Name` — verified against TimeWarp.OptionsValidation's `ServiceCollectionExtensions` source ("Default: Uses class name (DatabaseOptions → \"DatabaseOptions\")"). `WebAuthnOptions` carries no `[ConfigurationKey]` attribute, so the bound section is `"WebAuthnOptions"`, which does not exist — the appsettings values are silently ignored and the options always carry the C# property-initializer defaults. The repo's own precedent confirms the convention: `SampleOptions` binds the `"SampleOptions"` section (appsettings.json:26). This is fully masked today because the shipped appsettings values are byte-identical to the defaults (`RpId "localhost"`, `RpName "TimeWarp Architecture"`, empty `AllowedOrigins`), and `ValidateOnStart` cannot catch it (the defaults satisfy NotEmpty). The failure mode is deferred to the worst audience: a template consumer configuring production values (`RpId: "example.com"`, an explicit `AllowedOrigins` allowlist) has their configuration silently dropped — ceremonies keep using rpId `localhost` (hard failure, at least visible) and, worse, an operator who sets `AllowedOrigins` to lock down origins silently stays on the permissive empty-list dev fallback (any https origin whose host == RpId), a security-posture regression with no signal.
- Suggestion: Either rename the appsettings section to `"WebAuthnOptions"` or add `[ConfigurationKey("WebAuthn")]` to `WebAuthnOptions` (attribute keeps the friendlier section name). Add a cheap regression pin: an integration or options test asserting that a value set in test configuration (e.g. RpName) actually appears in the bound `IOptions<WebAuthnOptions>` — that test fails today.
- Status: open

### Issue 2 — Severity: suggestion
- File: source/container-apps/web/web-application/features/identity/complete-passkey-registration-handler.cs:12-13, 88-99
- Description: The duplicate-credential defense is check-then-act with no protection on the act: `FindCredentialByHandleAsync` (→ 409 when found) runs, then `Principal.Create` + `AddPrincipalAsync` + `AddCredentialAsync`. Two concurrent registrations of the same credential handle can both pass the Find check; the loser's `AddCredentialAsync` then throws the store's `InvalidOperationException` ("A credential with type ... already exists"), which nothing catches — it surfaces as an unhandled 500 instead of the 409 the contract advertises, and the already-persisted Principal from `AddPrincipalAsync` remains as an orphan with zero credentials. That directly contradicts the Design region's claim that "a duplicate-handle rejection never leaves an orphan Principal with no credential" — true for the checked path, false for the raced path. Real-world likelihood is low (authenticator-random credential ids), but the endpoint is anonymous and the payload attacker-supplied, so the interleaving is drivable deliberately.
- Suggestion: Wrap `AddCredentialAsync` in a catch of the store's duplicate `InvalidOperationException` returning the same 409 (and either compensate by removing the just-added principal or note the orphan possibility honestly in the Design region). Alternatively reorder so the credential (the uniqueness-bearing row) is added before the principal — though that inverts the FK-ish relationship — or accept and document.
- Status: open

### Issue 3 — Severity: suggestion
- File: tests/container-apps/web/web-server-integration-tests/Features/Identity/Passkey_Registration_Tests.cs:13-17
- Description: This Design region claims `WebTestServerApplication.HttpClient` is "one fresh instance per test method, matching this project's established convention" — contradicted by three things in the same commit: (a) the sibling fixture's Design region (integration-software-authenticator.cs:18-26) documents the app "constructed once and shared across every test method in a class (observed: a single 'WebApplication Started'/dispose pair per class)"; (b) `WebTestServerApplication` is registered `AddSingleton` in the testing convention; (c) the per-instance-random CredentialId fix exists precisely BECAUSE state persists across methods — if the host were fresh per method, the original fixed CredentialId could never have collided and the fix this commit documents would be unnecessary. The per-class sharing also means the HttpClient's cookie container carries session cookies across test methods within a class; today no test depends on per-method cookie isolation (each method asserts its own `Set-Cookie` header directly, which is the right pattern — e.g. Passkey_Authentication_Tests.cs:45-47, and the final `GetCurrentSession` assert there is corroboration rather than sole proof, since `RegisterPasskey` already issued a same-principal cookie), but a future test written against the false "fresh per method" claim will be order-dependent in a way that's painful to diagnose.
- Suggestion: Correct the Design region to state per-class (at minimum) sharing of the host, HttpClient, and cookie container, referencing the sibling fixture's region; optionally note that tests must assert `Set-Cookie` on the specific response rather than relying on ambient session state.
- Status: open

### Issue 4 — Severity: suggestion
- File: source/container-apps/web/web-contracts/features/identity/commands/complete-passkey-authentication.cs:36-44 (also complete-passkey-registration.cs:31-36)
- Description: Overlap note with the security review — flagging the contract-conventions half only. The registration command caps only `AttestationObject` (64KB); `CredentialId` and `ClientDataJson` are `NotEmpty` with no ceiling, and the authentication command caps nothing (`ClientDataJson`, `AuthenticatorData`, `Signature`, `CredentialId`, `UserHandle` all unbounded up to Kestrel's ~30MB body limit). Each unbounded field flows into `WebAuthnPayloadDecoder.TryDecode`, which allocates `GetMaxDecodedLength`-sized buffers before any validity check, on anonymous endpoints. The registration Design region's stated rationale ("a coarse size ceiling on the largest/most variable field") reads as if the other fields are implicitly small, but nothing enforces that. Deep DoS analysis belongs to the security reviewer; from the conventions side, the validator is the documented home for coarse size ceilings and it is inconsistent between the two commands.
- Suggestion: Add coarse `MaximumLength` ceilings to every base64url field on both completion commands (e.g. 2KB for CredentialId — spec caps credential ids at 1023 bytes; 16KB ClientDataJson; 8KB AuthenticatorData/Signature/UserHandle), mirroring the AttestationObject precedent.
- Status: open
