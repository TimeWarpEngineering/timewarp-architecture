# Round 1 — security

**Date:** 2026-07-19
**Scope reviewed:** commit 56882153 vs parent (security lens) — `source/libraries/timewarp-identity/ceremonies/webauthn/**`, the identity handlers, session/cookie plumbing, contracts, and the test tiers

## Summary

The hand-rolled verifier is sound on the load-bearing checks. I traced each WebAuthn §7.1/§7.2 step against the code: `type` is compared exactly per ceremony (`webauthn.create` vs `webauthn.get`, Ordinal); the challenge is compared as **decoded bytes** (`SequenceEqual`), so base64url padding/canonicalization pitfalls do not apply; origin is an exact allow-list match (with a documented https+host==RpId dev fallback); `rpIdHash == SHA256(rp.Id)`, the UP flag, and attested-credential-data presence are all enforced; the signed-data construction is the spec's `authData ‖ SHA256(clientDataJSON)` over the raw received bytes; ES256 uses DER (`Rfc3279DerSequence`), RS256 uses PKCS#1, hash fixed to SHA-256 both paths. Crucially, **algorithm confusion is correctly prevented**: the verification algorithm is derived from the *stored* COSE key's `kty`/`alg` (re-parsed from `storedCosePublicKey`), never from attacker-controlled per-request data, and `TryCreateVerifier` rejects any `kty`/`alg` inconsistency. The challenge is 32 CSPRNG bytes, consumed one-time **before** verification in both handlers, keyed by ceremony type, and the "expected challenge" is gated by the server store (`TryConsume`), so the tautological compare inside `Verify` is redundant-but-harmless rather than a client-trusted-challenge hole. All parsing is exception-safe (`Try*`/caught `CborContentException`/`FormatException`) on non-null adversarial input. Negative-path tests are honest (each corrupts exactly one field; the tampered-signature test would fail if verification were skipped). No exploitable auth-bypass found. Four hardening/defense-in-depth items below, no bugs.

## Issues

### Issue 1 — Severity: suggestion
- File: source/container-apps/web/web-application/features/identity/complete-passkey-authentication-handler.cs:79-88 (and the Design region at :10-17)
- Description: The quarantine check (`if (!principal.IsActive) return Quarantined();` at line 79-82, a distinct **403**) runs **before** `WebAuthnAuthentication.Verify` (line 87-88). The Design region justifies the distinguishable 403 by asserting "at that point the caller has already cryptographically proven possession of a real credential" — that claim is factually incorrect for the code as written: no signature has been verified when the 403 is returned. The result is a pre-authentication information-leak oracle: a caller who knows a valid `credentialId` but does **not** hold the private key can send a garbage signature and still learn "this credential maps to a quarantined/inactive account" (403) versus "active account" (400), distinguishing account states without proving possession. This also contradicts the no-enumeration posture the same handler documents for the unknown-vs-revoked case. (Currently latent: no path sets quarantine until 104-005, and a credential-bearing principal is auto-promoted to Keyed/`IsActive`, so the branch is effectively unreachable today — but the ordering ships now and becomes live when quarantine lands.)
- Suggestion: Move the `!principal.IsActive` check to **after** `Verify` succeeds, so the 403 is only reachable once possession is actually proven (making the Design region's stated invariant true), or collapse it into the generic 400 if leaking quarantine state pre-auth is unacceptable. At minimum, correct the Design comment to match the real ordering.
- Status: open

### Issue 2 — Severity: suggestion
- File: source/container-apps/web/web-contracts/features/identity/commands/complete-passkey-authentication.cs:34-43; source/container-apps/web/web-contracts/features/identity/commands/complete-passkey-registration.cs:28-36
- Description: Payload size caps are inconsistent and mostly absent. `CompletePasskeyAuthentication.Validator` applies `NotEmpty()` to `CredentialId`/`ClientDataJson`/`AuthenticatorData`/`Signature` but **no `MaximumLength`** on any field (and `UserHandle` is unvalidated). `CompletePasskeyRegistration.Validator` caps only `AttestationObject` at 64KB — `CredentialId` and `ClientDataJson` are uncapped. The plan §5 described the registration fields as "base64url, NotEmpty + 64KB max"; the implemented reality is a single field capped. Each uncapped field is base64url-decoded into a `byte[]` (handlers) and, for `ClientDataJson`, UTF-8/JSON-parsed. The only backstop is Kestrel's default `MaxRequestBodySize` (~30MB), so this is a bounded-but-large unbounded-allocation surface rather than a true DoS, but it is below the documented posture.
- Suggestion: Add `MaximumLength` caps to every base64url field on both completion commands (e.g. a small cap on `CredentialId` per the ≤1023-byte credential-id spec limit → ~1400 base64url chars; a modest cap on `ClientDataJson`/`AuthenticatorData`/`Signature`), matching the registration `AttestationObject` treatment.
- Status: open

### Issue 3 — Severity: suggestion
- File: source/container-apps/web/web-application/features/identity/complete-passkey-registration-handler.cs:79-89
- Description: The duplicate-credential guard is a check-then-act (`FindCredentialByHandleAsync` null-check at :79-83, then `AddPrincipalAsync` at :85-86, then `AddCredentialAsync` at :88-89). The store *does* enforce handle uniqueness atomically (`in-memory-principal-store.cs:138` `HandleIndex.TryAdd` under `WriteLock`, throwing `InvalidOperationException` on collision), so there is no double-registration integrity hole. However, under a concurrent race (two ceremonies with *distinct* valid challenges but the same authenticator/credentialId completing at once — the one-time challenge consume prevents the same-ceremony replay, but not two separate ceremonies), both callers pass the null-check, both call `AddPrincipalAsync` (a fresh Principal is minted), and the loser's `AddCredentialAsync` throws an **uncaught** `InvalidOperationException` → 500, leaving an orphan Provisional Principal with no credential. This directly contradicts the handler's Design claim (:12-13) that ordering "never leaves an orphan Principal with no credential" — that holds for the sequential 409 path, not the concurrent one. The orphan is inert (`IsActive` false, cannot authenticate), so impact is a stray store entry plus a 500 instead of a clean 409.
- Suggestion: Wrap `AddCredentialAsync` (and the preceding `AddPrincipalAsync`) so a store-level duplicate-handle `InvalidOperationException` is translated to the same `CredentialAlreadyRegistered()` 409 the sequential path returns, and/or reorder so the credential is added before the principal is durably committed (or compensate the orphan). Narrow window; acceptable to defer, but the Design region should not claim an invariant the concurrent path breaks.
- Status: open

### Issue 4 — Severity: suggestion
- File: source/libraries/timewarp-identity/ceremonies/webauthn/internal/cose-key.cs:142-149
- Description: At registration an RS256 COSE key is accepted with no minimum modulus size or exponent sanity check — `RSA.ImportParameters` validates structure but will happily import a short (e.g. 512-bit) modulus or a pathological exponent. Because registration mints a *new* Principal for the presenter, a weak key is self-inflicted (it only weakens the attacker's own account, not a victim's), so this is defense-in-depth, not an exploitable gap. Noted because a trust kernel accepting sub-2048-bit RSA public keys is a surprising default.
- Suggestion: Reject RSA moduli below 2048 bits (and optionally constrain the exponent to a small standard set) in `TryCreateVerifier`, mirroring the ES256 path's curve constraint. Optional.
- Status: open

## Coverage notes (not issues)

- Negative-path unit vectors are genuine and isolate one field each (wrong ceremony type, wrong/expired/reused challenge, wrong origin, rpIdHash mismatch, UP clear, missing attested data, credentialId mismatch, unsupported alg -8, malformed CBOR, `fmt:"packed"` + garbage attStmt accepted). The tampered-signature and tampered-authenticatorData tests genuinely exercise the crypto verify. Challenge-store tests cover one-time consume, unknown, wrong-ceremony-type, TTL (fake `TimeProvider`), and cap eviction.
- **Untested checks:** the quarantine ordering in Issue 1 (no test drives `!IsActive`, consistent with quarantine being unimplemented until 104-005); the concurrent duplicate-registration race in Issue 3; oversized-payload rejection in Issue 2 (there is no cap to test). None of these gaps hides a passing-but-wrong check — they are behaviors the current code does not (yet) implement.
