## Issues

### Issue 1 — Severity: suggestion
- File: tests/libraries/timewarp-identity-tests/in-memory-principal-store-concurrency-tests.cs:78-131 (and source/libraries/timewarp-identity/i-principal-store.cs:18-30)
- Description: Two explicitly documented port-contract clauses have no test. (a) **Caller-ahead conflict**: every conflict test in the suite exercises only the caller-*behind* case (Expected 0, Actual 1). The version check is `principal.Version != stored.Version` (in-memory-principal-store.cs:107), so a caller whose in-hand Version is *ahead* of the stored row (the realistic shape: an instance rehydrated from a different store instance, or any future bug that over-advances) also conflicts — with Expected > Actual — but nothing pins that; a regression to `<` / `>` comparison semantics would pass the current suite. (b) **Add persists Version as-is**: the port Design region states Add\* "persists the given instance's state as-is, including Version", and the implementation honors it (`principal.Snapshot(principal.Version)`, line 79; `credential.Snapshot(credential.Version)`, line 136) — but every test adds only freshly created version-0 instances, so the as-is clause for nonzero versions (observable by adding a Get-returned snapshot from store A into store B) is untested; a store that silently reset Version to 0 on Add would pass everything.
- Suggestion: Add two deterministic cases: (a) Get from store A after an update (v1), Add+Update flow against store B — or simply construct the ahead-state via two stores — asserting `ExpectedVersion > ActualVersion` in the thrown exception; (b) add a v1 snapshot to a fresh store and assert Get returns Version 1.
- Status: open

### Issue 2 — Severity: nit
- File: source/libraries/timewarp-identity/in-memory-principal-store.cs:37-42 (Design region), 211-218 (check)
- Description: The type/handle immutability branch in `UpdateCredentialAsync` — and therefore the Design region's carefully argued check order ("staleness dominates … a caller holding a stale-but-otherwise-valid credential should learn it is stale before learning about an unrelated type/handle mismatch") — is unreachable through the public surface: `Credential.Type`/`Handle` have no mutators, `CredentialId` is minted only inside `Create`, and `Snapshot` preserves both, so no caller can ever present a same-Id-different-handle credential (short of a v7 Guid collision). The branch is legitimate defense-in-depth against internal bugs, but the Design region presents the ordering as caller-observable behavior, and this also explains why no test covers it (it cannot be exercised without reflection). Same reasoning makes the `Credentials.TryAdd`-fails rollback branch in `AddCredentialAsync` (lines 136-140) publicly unreachable — duplicate id implies duplicate handle, which the HandleIndex check catches first.
- Suggestion: One sentence in the Design region acknowledging both branches are defensive (unreachable via the public API today) so a future reader doesn't hunt for the missing test or the caller who can trigger them.
- Status: open

### Issue 3 — Severity: nit
- File: source/libraries/timewarp-identity/in-memory-principal-store.cs:95-116, 194-224 (and i-principal-store.cs Design region)
- Description: The in-memory store throws `ConcurrencyConflictException` / `InvalidOperationException` *synchronously* from its Task-returning methods, while an EF-backed implementation will surface the same conditions as a faulted Task (thrown at `await`). A caller who separates task acquisition from awaiting (`Task t = store.UpdatePrincipalAsync(p); … await t;`) observes different behavior per implementation. This matters slightly more here than usual because the task's own rejected-alternative rationale ("in-memory vs EF stores diverge in behavior" was a reason to put conflict semantics on the port) makes cross-implementation behavioral parity an explicit goal, and the port Design region is silent on where the exception surfaces.
- Suggestion: Either one sentence in the `IPrincipalStore` Design region stating that Update\*/Add\* may throw synchronously or via the returned Task (callers must not assume faulted-task delivery), or make the in-memory methods deliver exceptions through the Task (e.g. `Task.FromException`) for parity. Doc sentence is the cheap option.
- Status: open
