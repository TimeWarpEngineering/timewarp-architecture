## Summary

The delta resolves both round-1 findings. `RelayChatClient.ToTurns` now maps every message with `ToTurn` and keeps a `(message, turn)` pair only when the contract's own `CompleteAgentChat.IsEmpty` says the turn is not empty, so the filter, the mapping, and the validator share one rule. The two new relay cases fail if the filter drifts or if `lastUser` is computed before filtering. I found no new defects.

## Prior findings

- M1 — resolved. `ReachesModel` is deleted. `relay-chat-client.cs:118-126` builds the pairs from `ToTurn(message)` and drops them on `IsEmpty(turn)` (the `using static CompleteAgentChat` at line 38). The validator calls the same method at `complete-agent-chat-contracts.cs:167`, and the only definition is the public static at `complete-agent-chat-contracts.cs:53`. A grep for `IsEmpty(` over `source` and `tests` finds those three call sites plus the test assertion, and no second copy of the rule. The edge kinds are pinned by `Relay_Leaves_Out_Messages_That_Map_To_An_Empty_Turn` (`ask-rejection-tests.cs:134-156`): reasoning-only assistant, whitespace-only assistant, non-image (PDF) user `DataContent`, and image-only user message. The role sequence `user|user|assistant|user` and the `ShouldAllBe(!IsEmpty)` assertion make a drift fail.
- M3 — resolved. The Design note now says the person's last message is found after the filter, so a surviving approval response never counts as it, and earlier tool pictures in the same turn are still sent (`relay-chat-client.cs:28-33`). `lastUser` is computed over `sent` at line 128. `Relay_Sends_A_Picture_Taken_Before_A_Rejected_Call_In_The_Same_Turn` (`ask-rejection-tests.cs:158-188`) pins it, and I traced that it fails under the old order. In that history the approval response is the last user-role message, at history index 4, and the picture result is at index 2. If `lastUser` were computed before the filter, `index > lastUser` would be false for the picture result, no picture turn would be built, and the expected role sequence `user|assistant|tool|user|assistant|tool` would not match.

## Checked, no defect

- Making `IsEmpty` public (`complete-agent-chat-contracts.cs:53`): it is a static method on the static partial `CompleteAgentChat`, not on `Command`, `Response`, or `Turn`, so serialization and the FastEndpoints contract generator never see it. The class already exposes public statics (`ImageMediaTypes`, `GetMockResponseFactory`). The nested `Validator` still resolves it by simple name. Build is 0/0 per the caller, so TWA0035, TW0001 and the other analyzers raise nothing. Public callers are limited to the relay and the new test. It would throw on a null `Turn`, but the validator's null handling is unchanged, and `ToTurn` never returns null.
- Message kinds against the single rule. A tool message with an empty-string result and a CallId is kept: `ToolCallId` is non-whitespace, which is also what the validator's "tool turn needs ToolCallId" rule needs. A tool message holding an `IToolResultImage` result is kept: `ToTurn` serializes the result to non-empty `ToolResult` and sets the CallId. A user message with whitespace text plus an image is kept, because `Images.Count > 0` makes it non-empty (`Text` stays `"   "`, which was the previous behavior). The one behavior difference from `ReachesModel` is a `FunctionResultContent` with an empty CallId and an empty or whitespace result. It was sent before and failed the validator with a 400. It is now dropped, which fits the task's goal. The orphan case does not arise from MEAI.
- Picture-turn placement: `runEnds` now looks at `sent[index + 1].Message.Role` (`relay-chat-client.cs:147`). The messages that get dropped (approval request, approval response, reasoning-only) are all non-tool, so a dropped message between two tool messages cannot split or merge a run. This is the same as round 1, and the new picture test exercises the dropped-message-after-tool-run case. The `pictureTurns` identity check and `KeepNewest` operate on the kept `turns` only, and dropped messages carry no images.
- `PictureResult` test record (`ask-rejection-tests.cs:214`): it mirrors `CatalogAgentCallResult` (`catalog-agent-functions.cs:283`), with `[property: JsonIgnore]` on `Image` so `JsonSerializer.Serialize` emits only `{"Summary":"{\"width\":640}"}`. That is a sane, non-empty `ToolResult`, and it does not try to serialize `DataContent`. The picture reaches the command through `result.Result is IToolResultImage { Image: { } image }`, not through the text. The test checks the role sequence, the picture turn text, and the base64 of `FakePng`. The `ScriptedModelApi` also runs the real validator (the 12-byte `FakePng` carries a valid PNG signature and base64 length), and `api.Failures.ShouldBeEmpty()` guards it. The test cannot pass vacuously, since the picture turn at `turns[3]` exists only if the picture was collected from a message before the surviving approval pair.
- `Relay_Leaves_Out_Messages_That_Map_To_An_Empty_Turn` also does not pass vacuously: with an unfiltered mapping, the whitespace, reasoning-only, and PDF turns would make the validator fail and `Failures` would be non-empty. `ChatMessage.Text` excludes `TextReasoningContent`, so the reasoning-only message maps to `Text = null` and is dropped.
- Hygiene: file names are unchanged and kebab-case. The Purpose and Design regions in all three files were updated to match the change (TWA0004). The only new using is `System.Text.Json.Serialization`, needed for `JsonIgnore`. Tests use only Jaribu and Shouldly. No estimates, no new dependencies, and `ToTurn` has no side effects, so mapping dropped messages is harmless.
